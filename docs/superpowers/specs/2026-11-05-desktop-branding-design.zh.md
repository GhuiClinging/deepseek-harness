## 目标和范围

生成可以安装、从访达打开且不依赖终端或源码目录的应用。所有者的产品拥有独立名称、图标、应用身份、存储和可编辑的默认角色。保留共享实现，供后续客户出包使用。新增业务工具、客户账号、多角色并行调度、Windows 或 Intel Mac 安装包以及下载发布，属于后续独立阶段。

<a id="current-implementation"></a>

## 现有实现

[打包入口](../../../apps/desktop/scripts/package-target.ts)选择 macOS ARM64、macOS x64 或 Windows x64，在准备目标资源前执行完整构建。[打包说明](../../../apps/desktop/packaging/README.zh.md)负责构建机要求、发行版本、签名和本地测试限制。

当前[打包配置](../../../apps/desktop/scripts/electron-builder-config.mjs)固定了产品名称、产物前缀和外部链接协议。[本地 macOS 配置](../../../apps/desktop/scripts/desktop-package-environment.mjs)固定应用 ID。[客户端构建配置](../../../scripts/client-build-environment.ts)会丢弃继承的标题覆盖值。[生产更新配置](../../../apps/desktop/scripts/desktop-auto-update-environment.mjs)使用上游下载地址。品牌选择需要明确传入这些所有者，单改文件名无法完成。

未打包启动依赖一个运行时目录变量，但生成的开发应用没有为访达启动导出这个变量。安装版通过应用内资源定位运行时。修复开发启动器与制作首个安装版是两项工作。

<a id="proposed-implementation"></a>

## 拟议实现

使用显式选择的公开品牌描述文件，统一驱动打包和内嵌产品信息。该描述文件是项目新增格式，不是现有 Harness 或 electron-builder 配置项。耗时构建前完成校验。签名秘密和用户模型凭据不进入描述文件。未选择品牌时保留现有行为。

描述文件提供稳定品牌标识、显示名称、应用 ID、外部链接协议、产物前缀、存储名称、图标路径和角色默认值。具体字段及选择命令在实施计划中确定。构建前解析全部素材路径；所选描述缺失必要值或包含非法值时，明确报错。所有者提供替代图标前先用中性临时文字图标；更换分发图标需要重新出包。

将所选值应用于安装后的应用名称和图标、欢迎页、原生菜单、窗口与侧栏产品标识及安装包信息。保留由语言字典管理的句子模板，以参数传入产品名。模型供应商名称、第三方版权和声明继续准确展示，不对 DeepSeek 文字进行全局替换。

每个品牌拥有独立的 Electron 数据目录和 Harness home，包含会话、设置、凭据、插件与日志。不会自动导入当前开发版或上游 profile。外部链接和可选命令注册不得占用其他品牌的身份。首个安装包无需安装全局终端命令。

首个本地验证产物明确使用手动升级，不连接上游更新或强制升级策略服务。身份与签名条件确认后，再完成签名分发阶段。自有品牌的签名打包必须显式选择产品升级方式，不得继承上游生产地址。本阶段不实现自动升级及新的升级服务。

建议首品牌使用现有 API Key 模型配置，不提供上游产品账号登录、余额、充值和用量入口。在本组合中关闭上游产品遥测和反馈会话上传。保留供应商名称和用户所选供应商的模型请求行为；模型调用与产品遥测分别处理。这些选择通过品牌组合应用，不改变未选择品牌的上游部署。设计确认包含这些产品选择。

按照品牌、目标平台和版本区分打包产物与完成记录。将所选公开身份保存在安装包内，防止后续运行静默换成其他客户身份。后续客户业务差异可以通过 profile 组合和插件扩展；本阶段不增加通用客户管理平台。

<a id="alternatives"></a>

## 备选方案

- 已选：共享核心，通过品牌描述和可选客户插件定制。在维护一套修复的同时，提供独立安装包。
- 统一产品、按账号定制需要维护较少安装包，但无法满足所有者选择的独立应用身份。
- 每客户维护独立分支允许任意差异，但会增加升级、签名和兼容性维护成本。仅在需求确实无法共享核心时采用。

<a id="delivery-and-verification"></a>

## 交付与验证

1. 确认品牌输入并审阅设计。遵循仓库发行规则，在实际打包前另行确认完整版本号。
2. 增加聚焦测试，覆盖描述校验、身份传递、品牌产物与存储隔离、未选择品牌时默认行为不变，以及拒绝误用上游更新配置。使用第二个测试身份验证共存，不交付第二个客户产品。
3. 更新受影响的 README、JSDoc 和语言字典对应的界面验证。为默认角色及可重建提示词增加无密钥录制会话快照，为品牌文案补充所属界面验证。复用现有 Session 事件，不新增事件类型或修改持久化格式。
4. 通过聚焦检查与完整构建后，再生成 macOS ARM64 产物。执行现有安装包运行时完整性与 smoke 检查，保留构建和打包证据。
5. 从外部目录通过访达打开安装后的应用。验证产品身份、Host 启动、独立存储和运行时资源定位。真实模型任务需要所有者配置凭据并明确测试范围，不能以构建成功代替。
6. 签名条件齐备后，对分发产物签名、公证并验证安装与启动。其他电脑兼容性验收与本机验收分别记录。下载发布仍是另行授权的操作。

已观察的准备结果：当前工作区在所有者的 Mac 上执行 `pnpm run package:desktop:mac:arm64:unsigned --check` 成功，报告本地配置与工具链有效，没有尝试签名或公证。这仅验证未改造打包流程的前提条件，不能证明拟议品牌实现或安装包已经可用。
